### P0 - Fix event join correctness

Current `join_event` can overbook under concurrent joins because it reads `joined_count`, checks capacity, increments in Python, and commits without locking.

Implement one of:

- PostgreSQL row lock: query event with `FOR UPDATE` inside the transaction.
- Atomic SQL update: update only where `joined_count < capacity`, then insert participation.

This is important because the assignment includes load testing, and write concurrency bugs are easy to demonstrate accidentally.

### P0 - Fix cache invalidation correctness

Current reads cache keys like:

```text
events:{city or all}:{sport or all}:{day or all}
```

But writes only delete the exact city/sport/day key. This can leave stale entries for:

- `events:Berlin:all:2026-07-06`
- `events:all:Football:2026-07-06`
- `events:all:all:2026-07-06`
- any `day=all` variants

Implement either:

- delete all affected variants explicitly, or
- maintain a versioned cache namespace per event date/city/sport, or
- keep the demo workload to exact city/sport/day and document the limitation.

Recommendation: delete affected variants explicitly because it is easiest to explain.

### P1 - Clarify overload strategy

The new `LoadSheddingMiddleware` is useful, but it is per backend node. That means with 5 backend nodes, aggregate accepted load is roughly 5x the per-node limit.

For the assignment, this is acceptable if documented as node-local load shedding. If we want stronger DB protection, add a Redis-backed global DB-work gate:

- before DB-heavy operations, increment shared Redis counter with TTL,
- reject with `503` if global in-flight DB work exceeds threshold,
- decrement in `finally`.

Recommendation: keep current per-node load shedding for now, but document the limitation clearly. Add Redis global gate only if there is time.
