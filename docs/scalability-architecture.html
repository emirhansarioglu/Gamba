Gamba Backend Scalability Plan

A concrete architecture for the prototyping assignment: scale the stateless FastAPI backend, keep PostgreSQL as the durable source of truth, use Redis as a shared remote cache and overload-control helper, and measure how far the backend tier scales before the stateful tier becomes the bottleneck.

Scale target: FastAPI backend Configurations: 1 / 3 / 5 nodes Primary metric: successful requests/sec Source of truth: PostgreSQL Shared cache: Redis

Architecture

The backend fleet is horizontally scaled. Nginx and the stateful services are intentionally kept single-node for the assignment so the experiment is focused and reproducible.

Users / K6 Browser traffic and load tests
Nginx Static frontend, reverse proxy, round-robin load balancing
Backend 1 FastAPI, stateless, JWT validation, event API
Backend 2 Same code, no local durable state
Backend N 1, 3, or 5 nodes depending on deployment
Overload Gate Reject early with 429 before DB work when capacity is exceeded
Redis Remote shared cache, cache hit/miss metrics, optional shared rate/load counters
PostgreSQL Durable users, events, participations, capacity checks
Metrics /metrics, structured logs, K6 result table
Known Bottleneck Stateful tier eventually limits write-heavy load

Request Flow

Read path

Browse events

  1. Nginx sends request to one backend node.
  2. Backend checks JWT and overload gate.
  3. Backend checks Redis key such as events:Berlin:Football:2026-07-03.
  4. On hit, return cached list. On miss, query PostgreSQL and store result with TTL.
Write path

Create or join event

  1. Backend validates role and request.
  2. Capacity-sensitive writes go to PostgreSQL in a transaction.
  3. Backend invalidates affected Redis keys.
  4. Response includes updated capacity/join count.
Failure behavior

Protect the DB

  1. If Redis is slow, cap fallback traffic to PostgreSQL.
  2. If overload gate is closed, return 429 quickly.
  3. Use timeouts and bounded retries, not unlimited waiting.
  4. Log the dependency that caused latency or failure.

Why Remote Redis Still Makes Sense

What Redis gives us

  • A shared cache used by all backend nodes.
  • Lower-cost reads than repeated PostgreSQL queries.
  • Cache state that survives backend deployments and cold starts.
  • A place for shared counters if rate limiting must protect PostgreSQL globally.

What Redis does not give us

  • It is not the source of truth.
  • It does not remove the need to handle stale data.
  • It does not make writes scale like reads.
  • It adds an extra service that must be monitored.

AWS Builders Library Patterns Applied

These are the article ideas that most directly shape the Gamba design. Some articles are useful as "do not overbuild this" guidance.

Article / Pattern Decision for Gamba How it appears in the plan
Caching challenges and strategies Use Remote Redis as side cache for repeated event-list reads. Track hit rate, miss rate, Redis latency, and DB fallback rate.
Using load shedding to avoid overload Use Reject excess requests with 429 before expensive DB work. This is the main answer to requirement 3.
Putting the smaller service in control Use lightly Let the constrained tier define capacity: DB-work concurrency and Redis/DB fallback rate should be capped by what the stateful tier can handle.
Instrumenting distributed systems for operational visibility Use Prometheus counters/histograms for request rate, p95 latency, cache hits/misses, 429s, DB latency, and error categories.
Timeouts, retries, and backoff with jitter Use Bound Redis/DB calls. Avoid retry storms. If clients retry after 429/5xx, they should use backoff and jitter.
Making retries safe with idempotent APIs Use for writes if time allows Add an idempotency key to event creation or join attempts if the frontend/K6 retries writes.
Using dependency isolation to contain concurrency overload Use conceptually Separate limits for Redis and PostgreSQL work so cache failure cannot flood DB connections.
Reliability, constant work, and a good cup of coffee Use selectively Keep code paths predictable: fixed-size result pages, bounded work per request, no unbounded queue processing in API handlers.
Avoiding insurmountable queue backlogs Mostly avoid queues The app is request/response. Do not add background queues just to satisfy the assignment. If a queue is added, bound it and measure depth.
Avoiding fallback in distributed systems Use as caution Redis failure should not cause unlimited fallback to PostgreSQL. Fallback must be capped or load-shed.
Fairness in multi-tenant systems Optional If needed, rate-limit by user/IP so one load-test user cannot consume all capacity. Not central because Gamba is not truly multi-tenant.
Workload isolation using shuffle-sharding Do not implement Too complex for this app. Mention as future work for tenant/city-level isolation if the app became multi-tenant.
Leader election in distributed systems Do not implement No single backend node should become special. PostgreSQL transactions handle write correctness instead.
Minimizing correlated failures Use in evaluation Deploy identical backend nodes, but discuss the correlated-failure risk of shared Redis, shared PostgreSQL, and one Nginx VM.
Challenges with distributed systems Use as framing Keep the design simple. Avoid unnecessary distributed coordination and be explicit about partial failure modes.

Assignment Requirement Mapping

Requirement Answer
Stateful and stateless components FastAPI nodes are stateless. PostgreSQL is durable state. Redis is shared ephemeral cache state.
1 / 3 / 5-node deployments Deploy 1, 3, and 5 FastAPI backend VMs behind the same Nginx entry point.
Vertical scaling bonus Repeat the same tests with a larger VM type if time and budget allow.
Overload mitigation Use load shedding or a shared Redis-backed token bucket/concurrency gate before DB work.
Two additional lecture strategies Redis caching and operational instrumentation. If observability is considered support rather than a strategy, use dependency isolation/query optimization as the second strategy.
Measured scalability result K6 results table showing successful requests/sec, p95 latency, error rate, 429 rate, and cache hit rate for each deployment.

Implementation Plan

1. Baseline Run local app, seed users/events, verify health, auth, list, create, and join.
2. Correctness Make join transaction-safe and fix cache invalidation for affected query variants.
3. Overload Add shared limiter or DB-work concurrency gate. Emit 429 metrics.
4. Measurement Extend K6 with read-heavy and mixed scenarios. Record p95, RPS, errors, hit rate.
5. Deploy Provision 1/3/5 backend nodes with Terraform, run identical tests, document limits.

Expected Results

Read-heavy traffic

Should scale best because repeated event-list requests hit Redis after warmup. Throughput should improve from 1 to 3 nodes and may improve less from 3 to 5 if Redis, Nginx, or the VM network becomes limiting.

Mixed read/write traffic

Should scale less cleanly because joins and creates must update PostgreSQL and invalidate cache entries. This is the honest place to show that the single DB is the main write bottleneck.

Risks To Say Out Loud

Single DB bottleneck

One PostgreSQL node is correct for the assignment but limits write-heavy throughput.

Cache dependency

Redis helps reads, but cache outage or cold cache can shift load back to PostgreSQL.

Per-node rate limits

An in-memory limiter multiplies accepted traffic by node count. Use Redis if the goal is to protect the DB globally.
